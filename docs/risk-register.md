# EP-Governance Risk Register

## Version

1.0 — Phase 0 Specification Intake

## Date

2026-07-29

## Purpose

This document catalogs project-level risks identified during Phase 0 specification intake. Risks span technical, schedule, security, and operational categories. Each risk includes a mitigation strategy and an owner. The register will be updated throughout the project lifecycle as risks are realized, mitigated, or newly identified.

Status legend: Identified (risk recognized, mitigation not yet started), Mitigating (mitigation in progress), Closed (risk resolved or accepted), Monitoring (mitigation implemented, watching for recurrence).

| ID | Risk | Category | Likelihood | Impact | Mitigation | Owner | Status |
|---|---|---|---|---|---|---|---|
| RSK-001 | Ed25519 implementation bugs in token signing or verification. The PyNaCl library or custom key management code could contain subtle errors that produce forgeable tokens, break verification across key rotations, or mishandle key serialization. | Technical | Medium | High | Use the well-audited PyNaCl library (libsodium bindings) rather than implementing Ed25519 from scratch. Write property-based tests for sign/verify round-trips, key serialization, and key rotation scenarios. Include negative tests (tampered payload, wrong key, expired token). ADR-0003 documents the signature format decision. Add fuzzing for the canonical JSON -> sign -> verify pipeline. | Core development team | Identified |
| RSK-002 | SQL classifier evasion: crafted SQL statements that parse differently than expected, bypassing policy matching. Multi-statement inputs, dialect-specific syntax, obfuscated queries, or comments could trick the classifier into categorizing a DROP as a SELECT. | Security | Medium | High | Use a robust SQL parser (sqlglot preferred — see AMB-009) that produces a full AST. Classify based on AST node types, not string matching. Reject multi-statement inputs unless explicitly supported. Default to highest-risk classification when parsing is ambiguous. Log all classification decisions with the parsed AST for audit. Add adversarial test cases specifically designed to evade classification. | Core development team | Identified |
| RSK-003 | Shell classification incompleteness: the shell parser cannot fully classify all valid shell constructs. Piped commands, subshells, process substitutions, aliases, functions, and eval constructs may escape classification. | Technical | High | Medium | Follow the v1.1.1 escalating treatment model: known safe commands parsed with shlex, complex commands parsed with bashlex if reliable, opaque or unparseable scripts classified as `shell.exec.opaque` (high-risk, require_approval or deny by default). Never claim complete semantic classification. Document known limitations. Maintain a denylist of dangerous executables (rm, dd, mkfs, chmod 777, etc.). | Core development team | Identified |
| RSK-004 | Concurrent audit insertion performance bottleneck. Per-lattice audit heads with row locking serialize all audit writes for a lattice. Under high throughput (many agents, many transitions), the lock contention on ep_audit_heads could become a performance bottleneck. | Technical | Medium | Medium | Per-lattice chains already reduce contention versus a global chain (v1.1.1 §5 design). Monitor lock wait times in testing. If contention is observed, consider batching audit writes or sub-lattice partitioning. The audit head lock is held for a very short transaction (lock, compute hash, insert, update head, commit). Benchmark with 10+ concurrent writers in Phase 3 integration tests. | Core development team | Identified |
| RSK-005 | Policy condition language limitations. The chosen condition language (CEL, Cedar, or Rego — see AMB-008) may not support all required expression types: time-window conditions, cross-field references, complex resource matching, or custom functions needed for risk domain evaluation. | Technical | Medium | High | Evaluate CEL, Cedar, and Rego against a comprehensive test suite of policy conditions before selection (ADR-0001). Define the minimum required expression types in Phase 1. If the chosen language is insufficient, fall back to a restricted JSON-logic subset for simple conditions and require approval for conditions the language cannot express. Never allow the condition engine to fail open — errors must fail closed (deny or require_approval). | Core development team | Identified |
| RSK-006 | Deployment isolation not achieved in practice. The v1.1.1 §8 enforced mode requirements (no direct tools, no credentials in agent env, no Docker/SSH sockets, network restrictions) are deployment constraints that EP-Governance cannot enforce by itself. If operators do not follow the deployment guide, the system operates in advisory mode regardless of EP_MODE=enforced, but users may believe enforcement is active. | Security | High | High | Document deployment requirements prominently in SKILL.md, README.md, and a dedicated deployment guide. Add a startup check that warns if EP_MODE=enforced but isolation indicators suggest advisory (e.g., agent has shell access, credentials detected in environment). Make the warning explicit: "Enforced mode is configured but runtime isolation is not detected — operating in advisory mode." Do not claim enforcement guarantees without verified isolation. | Core development team + Operators | Identified |
| RSK-007 | Database tampering by DBA or someone with direct database access. A privileged database user can UPDATE or DELETE audit events, modify transition stages, or alter policy state. EP-Governance explicitly does not provide cryptographic guarantees against this (v1.1 §23.2, §1.4). | Security | Low | High | The hash-chained audit log makes tampering detectable (any modification breaks the chain). Use restricted database roles: the EP service role has INSERT on ep_events, no UPDATE/DELETE. Other roles have no direct access. Document this as a known limitation — EP-Governance is a governance and audit system, not a cryptographic vault. Recommend database-level auditing (PostgreSQL pg_audit) and restricted DBA access for high-security deployments. Consider signed external checkpoints for high-assurance scenarios. | Core development team | Identified |
| RSK-008 | Network partition during execution. The proxy is executing an action and loses network connectivity to the EP database before it can record the result. The transition remains in `executing` state indefinitely. The actual action may have succeeded or failed. | Operational | Medium | High | Implement the v1.1.1 `execution_uncertain` stage for transitions where the proxy cannot report a terminal result. The proxy uses a unique execution-attempt ID and a timeout. If no result is received within the timeout, the transition moves to `execution_uncertain` and requires manual reconciliation by an operator. The agent is instructed not to assume success or failure (SKILL.md rule 3). Add a reconciliation CLI command for operators. | Core development team | Identified |
| RSK-009 | Clock skew affecting token expiry validation. If the EP server and the proxy have different clock readings, a token may be considered valid by one and expired by the other, or the `expires_at` check may be incorrect. | Technical | Low | Medium | Use UTC timestamps throughout (ISO 8601 UTC per ADR-0002). Require NTP synchronization on all hosts running EP or the proxy. Add a clock-skew check at proxy startup that compares its clock with the EP server and warns if delta exceeds 5 seconds. Token TTL default is 300 seconds (5 minutes) — a skew of a few seconds is within tolerance. For tight tolerance scenarios, reduce token TTL and require stricter sync. | Core development team | Identified |
| RSK-010 | Key rotation complexity for Ed25519 signing keys. Rotating the signing key requires: generating a new keypair, distributing the new public key to all proxies, signing new tokens with the new key, and accepting old-key tokens during a transition window. If the transition window is misconfigured, valid tokens may be rejected or stale keys may be accepted too long. | Operational | Medium | Medium | Implement key rotation with an explicit transition window: both old and new public keys are accepted by proxies during the window. New tokens are signed with the new key. The transition window is configurable (default 1 hour). Log key rotation events to the audit chain. Provide a CLI command for key rotation: `ep-governance rotate-signing-key`. Test rotation in integration tests. Store key metadata (key_id, created_at, rotated_at, status) in the database. | Core development team | Identified |
| RSK-011 | Imported malicious policies. A transfer package from an untrusted source could contain policies that grant excessive permissions (e.g., allow all actions on all resources). If imported as active, these policies immediately weaken governance. | Security | Medium | High | v1.1.1 additional corrections specify: imported policies start as `imported_pending_review`, not active. Only activate when signer and source are explicitly trusted. Implement trust verification: check the signer's identity against a trust list, verify the package signature, and require operator approval before activation. Log all import operations to the audit chain. Display imported policies prominently in the CLI for review. Never auto-activate imported policies. | Core development team | Identified |
| RSK-012 | Proxy crash leaving transitions in uncertain state. The governed proxy crashes or is killed mid-execution. The transition is in `executing` state but no result will be reported. The action may have partially completed. | Operational | Medium | High | Implement the `execution_uncertain` stage and a timeout-based reconciliation mechanism. The proxy records execution-start and execution-attempt ID. If no terminal result arrives within a configurable timeout, the transition moves to `execution_uncertain`. An operator uses `ep-governance reconcile <transition_id>` to manually set the terminal state after investigating. The proxy must be idempotent for retryable operations. For non-idempotent operations, the operator must investigate before setting the terminal state. | Core development team | Identified |
| RSK-013 | Schema migration failures. Database schema migrations may fail partway, leaving the database in an inconsistent state. Migration up/down reversibility may not work for all changes (e.g., adding a CHECK constraint to a table with existing invalid data). | Technical | Medium | High | Write migration up and down scripts for both PostgreSQL and SQLite. Test migrations against realistic data in CI. Add pre-migration validation (check for data that would violate new constraints). Use transactional migrations where possible (PostgreSQL DDL is transactional). For SQLite, use BEGIN IMMEDIATE. Never run migrations against a production database without a backup. Document the migration procedure. Add a `ep-governance migrate --dry-run` command to preview changes. | Core development team | Identified |
| RSK-014 | Multi-agent branch conflicts. Multiple agents working on the same branch may repeatedly hit stale_head errors, causing retry storms, livelock, or degraded throughput. If optimistic concurrency is too aggressive, agents may waste cycles proposing transitions that always fail. | Technical | Medium | Medium | The optimistic concurrency model (expected_head_id + expected_version) is the correct approach. Implement exponential backoff for stale_head retries (max 3 retries by default, configurable). Encourage agents to work on separate branches when possible. Work claims (ep_work_claims) prevent two agents from working on the same region simultaneously. Monitor stale_head rates in testing. If contention is chronic, recommend branch separation or work-claim usage. | Core development team | Identified |
| RSK-015 | Treating unit tests as proof of production readiness. Unit tests with deterministic inputs may pass while the system fails in production due to concurrency, network partitions, real SQL dialects, or edge cases not covered by unit tests. This is especially dangerous for a governance system where false confidence could lead to insufficient enforcement. | Operational | High | High | Unit tests are necessary but not sufficient. The testing strategy must include: property-based tests (hypotesis/pytest) for hash determinism, canonical JSON, XID uniqueness, and policy evaluation; integration tests against PostgreSQL via Testcontainers (not just SQLite); concurrency tests with multiple parallel agents; adversarial tests for classifier evasion; and security tests for token forgery and audit tampering. ADR-0004 explicitly states: SQLite-only tests do not substitute for PostgreSQL integration tests. Define coverage targets in Phase 1. Never claim production readiness based on unit tests alone. | Core development team | Identified |
| RSK-016 | Condition language sandbox escape. The policy condition engine (CEL, Cedar, or Rego) could have security vulnerabilities that allow arbitrary code execution, network access, or filesystem reads from within a policy condition expression. | Security | Low | High | Choose a language with a proven sandbox (CEL is side-effect-free by design; Cedar is purpose-built for authorization). Disable all external function calls and I/O in the evaluation context. Run the evaluator in a restricted Python execution context (no subprocess, no filesystem access). Add fuzzing tests for the condition engine. Monitor for CVEs in the chosen library. Fail closed on any evaluation error. | Core development team | Identified |
| RSK-017 | Canonical JSON determinism across platforms. If the canonical JSON serialization produces different output on different Python versions, platforms, or float representations, audit hash verification will fail for cross-platform verification. | Technical | Medium | High | ADR-0002 specifies fixed-point integer representation for governed numeric values (risk_milliunits, percentage_basis_points, budget_milliunits) to eliminate float ambiguity. The canonical JSON function must be tested with property-based tests across Python 3.12+ versions. Pin the Python version range. Include cross-platform verification tests (serialize on one platform, verify on another). Document the 10 canonical JSON rules explicitly and test each. | Core development team | Identified |
| RSK-018 | XID collision under high concurrency or clock rollback. The rs/xid format uses a 3-byte counter that wraps after 16M IDs per timestamp+machine+PID. Under extreme concurrency, or if the clock rolls back, collisions are possible. | Technical | Low | Medium | The XID generator already handles clock rollback (uses last_used_timestamp + 1). Collision retry handles PK violations (up to 3 attempts). Fork safety re-seeds the counter. Test the generator under high concurrency to verify no collisions within expected throughput. If collisions exceed retry capacity, the operation fails explicitly (better than silent corruption). Monitor collision rates in production. | Core development team | Identified |
| RSK-019 | Project scope creep beyond the 8-phase plan. The design documents are extensive (25 sections in v1.1, 8 addendum corrections in v1.1.1). There is a risk of attempting to implement all features simultaneously rather than following the phased approach. | Schedule | High | Medium | Strictly follow the phased work plan (work-plan.md). Each phase has explicit gate criteria. Do not begin Phase N+1 until Phase N gates are met. Use the traceability matrix to track which requirements are satisfied by which phase. Defer non-critical features (embeddings, NATS, merge semantics) to later phases or post-MVP. | Project lead | Identified |
| RSK-020 | Insufficient test infrastructure for PostgreSQL integration tests. The project requires Testcontainers for PostgreSQL integration tests, but the test infrastructure may not be set up, causing developers to rely on SQLite-only tests that do not validate production behavior. | Schedule | Medium | High | Set up Testcontainers (or a local PostgreSQL Docker container) in Phase 3 before writing any database-layer tests. ADR-0004 requires all integration and concurrency tests to run against PostgreSQL. Label SQLite-only tests explicitly. Add a CI check that fails if integration tests are not run against PostgreSQL. Provide a docker-compose.test.yml for local testing. | Core development team | Identified |
