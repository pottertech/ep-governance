# EP-Governance Ambiguity Register

## Version

1.0 — Phase 0 Specification Intake

## Date

2026-07-29

## Purpose

This document catalogs all ambiguities, contradictions, and open questions found between `ep-governance-design-v1.1.md` (v1.1) and `ep-governance-design-v1.1.1.md` (v1.1.1), plus remaining open questions from the v1.1 design. Where v1.1.1 resolves an ambiguity, the resolution is recorded. Items still open require a decision before the dependent phase can proceed.

Status legend: Resolved (v1.1.1 provides a controlling interpretation), Open (no resolution yet; decision required).

| AMB-001 | v1.1 section 5.1 and 11.2 list `ep_nodes.status` as including intention states: `proposed`, `authorized`, `executing`, `failed`, `denied`, `cancelled`, `expired`. This conflates transition lifecycle stages with realized graph states. Denied proposals never enter the graph. Only successfully executed states should become committed nodes. | v1.1 §5.1, §11.2 (ep_nodes.status CHECK); v1.1.1 §2 (Only Realized States Become Graph Nodes) | v1.1.1 §2 resolves: `ep_nodes.status` CHECK changes to `('committed', 'quarantined', 'at_risk', 'superseded', 'archived')`. Transition stages remain in `ep_transitions.stage`. A new ep_node row is inserted ONLY when a transition reaches `succeeded`. | Resolved | Implement the v1.1.1 §2 schema. ep_nodes contains only realized states. The full transition lifecycle (proposed through terminal states) lives in ep_transitions. Use the v1.1.1 transition record shape with inline proposed_state. |
| AMB-002 | v1.1 section 5.2 specifies HMAC-SHA256 for authorization token signing: a shared key known to both EP and the proxy. This means a compromised proxy can mint authorizations. v1.1.1 additional corrections specify Ed25519 asymmetric signatures. | v1.1 §5.2 (signature: HMAC-SHA256); v1.1.1 additional corrections (Ed25519) | v1.1.1 resolves: use Ed25519. EP holds the private signing key; proxies hold only the public verification key; agents receive neither. ADR-0003 accepts this decision. | Resolved | Implement Ed25519 signing via PyNaCl. The token payload is canonical JSON of the token fields (excluding the signature). The database stores the authorization record and token hash, not the private key. Support key rotation (signing with new key, verifying with old key during transition window). |
| AMB-003 | v1.1 section 7.4 states two transitions from the same parent can both commit to the same branch ("This is a branch, not a conflict"). But a branch has one `head_node_id`, and each node has one `branch_id`. Two children of the same parent cannot both be the head of the same branch. | v1.1 §7.4 (Branching); v1.1.1 §1 (One Branch, One Head) | v1.1.1 §1 resolves: a branch always has exactly one head. The first transition may advance the existing branch head. The second must fail with `stale_head`. To proceed, the second agent explicitly creates a new branch via `ep-governance create-branch`. No schema change needed. | Resolved | Implement the v1.1.1 §1 branch model. Optimistic concurrency on (head_node_id, version) ensures only one transition advances a branch head. The `create-branch` CLI command creates a new branch row linked to the parent branch's current head. |
| AMB-004 | v1.1 section 23.3 and 11.2 define the audit hash formula as `SHA-256(event_data || previous_hash)`. This does not protect `event_type`, `principal_id`, `created_at`, or `sequence`. Someone could alter metadata without breaking the chain. | v1.1 §11.2 (ep_events.event_hash), §23.3; v1.1.1 §4 (Audit Hashing Includes Full Canonical Event Envelope) | v1.1.1 §4 resolves: the hash covers the complete immutable envelope: sequence, event_id, event_type, event_data, principal_id, created_at, previous_hash. Canonical JSON serialization rules (10 rules) defined. ADR-0002 accepts the canonical JSON rules. | Resolved | Implement the v1.1.1 §4 canonical envelope hash. The canonical_json function must follow the 10 rules (UTF-8, sorted keys, no whitespace, ISO 8601 UTC, integer/float representation, null/boolean, array order, no duplicate keys, no comments). Property-based tests must verify hash determinism. |
| AMB-005 | v1.1 section 11.2 (Audit) says "Agents and proxies can INSERT into ep_events but cannot UPDATE or DELETE." Append-only does not mean trustworthy — a malicious agent could insert fabricated events. | v1.1 §11.2 (ep_events access); v1.1.1 §5 (Audit Insertion Is Serialized) | v1.1.1 §5 resolves: only the EP-Governance service writes audit events. Agents and proxies submit operations to EP; EP authenticates the caller, performs the operation, and writes the resulting audit event. Actor separation: actor_principal_id, authenticated_caller_id, event_writer_id. Per-lattice audit heads with row locking (ep_audit_heads table). | Resolved | Implement the v1.1.1 §5 model. The EP service is the sole writer to ep_events and ep_audit_heads. DB permissions: only EP service role can INSERT into ep_events; no role can UPDATE or DELETE. Agents authenticate to EP via API key; EP validates and writes the event. Per-lattice chains via ep_audit_heads with FOR UPDATE locking. |
| AMB-006 | v1.1 sections 9.2, 10.2, and 11.2 use UT terminology (`ut_cost`, `ut_deltas`, `ut_after`) from an older single-number cost model, while simultaneously redefining UT as a per-domain risk ledger. The schema and API still use the old field names. | v1.1 §9.2, §10.2, §11.2 (ut_cost/ut_deltas/ut_after); v1.1.1 §7 (Risk-Ledger Terminology) | v1.1.1 §7 resolves: replace `ut_cost` -> `risk_increment`, `ut_deltas` -> `risk_assessments`, `ut_after` -> `residual_risk_after`. Mitigations require verified evidence (evidence_type, evidence_uri, evidence_hash, verified_by, verified_at, expires_at). | Resolved | Implement the v1.1.1 §7 terminology throughout the schema, API, and code. Rename columns in ep_transitions: `ut_deltas` -> `risk_assessments`, add `residual_risk_after`. Extend ep_risk_mitigations with evidence fields. Mitigation credit comes from policy (verified by policy_approver or operator), not agent self-attestation. |
| AMB-007 | v1.1 section 7.4 mentions a merge operation ("A merge operation can reconcile branches when needed") but does not define merge semantics. v1.1.1 does not address merge semantics. v1.1 §25.7 lists branch merge semantics as an open question. | v1.1 §7.4, §25.7; v1.1.1 (not addressed) | Not resolved by v1.1.1. v1.1.1 §1 clarifies that divergence requires new branches, but does not define how branches merge back. | Open | Defer merge implementation beyond Phase 6. For Phase 6, support branch creation and independent advancement. Implement merge as a manual, policy-governed transition in a later phase. A safe default: merge creates a new node with edges from both branch heads, requires operator approval, and logs a comprehensive audit event. Do not implement automatic conflict resolution. |
| AMB-008 | v1.1 section 4.4 uses a custom typed JSON schema for policy conditions. v1.1 §25.1 asks whether to evaluate CEL, Rego/OPA, Cedar, or JSON Logic. v1.1.1 additional corrections say to evaluate CEL and Cedar before Phase 2. | v1.1 §4.4, §25.1; v1.1.1 additional corrections | v1.1.1 partially resolves: directs evaluation of CEL and Cedar before Phase 2. ADR-0001 is proposed (pending evaluation). A custom language will not be built unless a written decision demonstrates CEL, Cedar, and Rego are all unsuitable. | Open | Perform CEL vs Cedar vs Rego evaluation in early Phase 2. Decision must be recorded in ADR-0001 before implementing policy conditions. Until decided, use a minimal JSON-logic subset for unit testing. |
| AMB-009 | v1.1 section 10.1 requires SQL AST parsing for server-side classification. v1.1 §25.2 asks which Python SQL parser to use: sqlglot, sqlparse, or moSQL. v1.1.1 does not specify. | v1.1 §10.1, §25.2; v1.1.1 (not addressed) | Not resolved by v1.1.1. | Open | Evaluate sqlglot (supports most dialects, produces proper AST), sqlparse (simpler, less complete AST), and moSQL. Prefer sqlglot based on v1.1's own analysis. Record decision in an ADR. The classifier must extract: operation type (SELECT/INSERT/UPDATE/DELETE/DROP/ALTER/etc.), target objects (tables, schemas, databases), and classify risk domain. Must handle multi-statement inputs and reject ambiguous parsing. |
| AMB-010 | v1.1 section 10.1 requires shell command parsing for classification. v1.1 §25.3 asks whether to use shlex (basic), bashlex (full bash AST), or a custom classifier. v1.1.1 additional corrections clarify: do not promise complete semantic classification; use escalating treatment (known safe commands parsed, opaque scripts as shell.exec.opaque, unrecognized require approval or deny by default). | v1.1 §10.1, §25.3; v1.1.1 additional corrections | v1.1.1 partially resolves the classification approach (escalating treatment) but does not specify the parser library. | Open | Use shlex for known-safe commands (simple executables with arguments). Use bashlex for complex commands (pipes, redirects, subshells) if it proves reliable in testing. For opaque/unparseable scripts, classify as `shell.exec.opaque` (high-risk, require_approval or deny by default). Do not attempt full semantic equivalence. Record the parser decision in an ADR. The escalating treatment model from v1.1.1 is the governing approach. |
| AMB-011 | v1.1 section 9.2 defines risk domains and their tracking fields but does not specify default `inherent_risk` values or thresholds. v1.1 §25.6 asks what the defaults should be and whether they should be configurable per project. v1.1.1 does not specify defaults. | v1.1 §9.2, §25.6; v1.1.1 §7 (terminology only) | Not resolved by v1.1.1. v1.1.1 §7 defines the API representation (risk_assessment object with threshold field) but not the default values. | Open | Define conservative defaults in Phase 1: production_database inherent_risk=80 threshold=50, external_communications inherent_risk=60 threshold=40, deployment inherent_risk=70 threshold=50, data_privacy inherent_risk=75 threshold=50, security inherent_risk=85 threshold=30. | AMB-012 | v1.1 section 6.2 says global policies require human co-approval, but the schema (§11.2 ep_policies) allows a policy to be inserted directly as `active` with no activation workflow. | AMB-013 | v1.1 section 5.2 says the token is single-use with a `used` boolean. Two proxy requests could read `used = false` simultaneously and both execute. This is a race condition. | v1.1 §5.2 (used boolean); v1.1.1 §3 (Atomic Claiming) | v1.1.1 §3 resolves: token claiming is an atomic UPDATE ... WHERE used = FALSE AND expires_at > NOW() RETURNING. ## Summary

| Status | Count |
|---|---|
| Resolved | 13 |
| Open | 7 |

The 13 resolved ambiguities have controlling interpretations from v1.1.1. The 7 open ambiguities require decisions before the dependent implementation phases can proceed. Specifically:

- AMB-007 (branch merge semantics) blocks Phase 6 merge features
- AMB-008 (condition language) blocks Phase 2 policy condition implementation
- AMB-009 (SQL parser) blocks Phase 2 SQL classification
- AMB-010 (shell parser) blocks Phase 2 shell classification
- AMB-011 (risk domain defaults) blocks Phase 4 risk ledger implementation
- AMB-018 (retention policy details) is low-priority but needed before production
- AMB-019 (versioning policy) blocks Phase 1 formal specification
- AMB-020 (branch merge status) is coupled to AMB-007

Each open item should be resolved via an ADR or specification update before the blocking phase begins.
